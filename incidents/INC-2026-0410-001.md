## Summary

During a `docker buildx build` operation using the `multiarch` builder, up to **15 concurrent and parallel image layer downloads** were observed, consuming excessive bandwidth. This occurred despite `max-parallelism = 1` being set in the builder's `buildkitd.toml` configuration.

## Root Cause Analysis

### Immediate Cause

The `max-parallelism = 1` setting in `buildkitd.toml` was correctly applied, as confirmed by `docker buildx inspect`:

```toml
[worker.oci]
  max-parallelism = 1
```

However, this configuration **limits concurrent build steps**, not concurrent layer downloads within a single image pull. When BuildKit pulls a single base image, it fetches all layers of that image in parallel as part of a single step — this behavior is **not controlled** by `max-parallelism`.

### Contributing Factors

- BuildKit has no native configuration knob to limit per-image layer download concurrency.
- The `docker-container` driver delegates image pulling to BuildKit's internal layer fetcher, which defaults to maximum parallelism per pull.
- The `multiarch` builder targets multiple platforms (`linux/amd64`, `linux/amd64/v2`, `linux/amd64/v3`, `linux/386`), potentially multiplying the number of simultaneous layer downloads across platform variants.

## Mitigation Options

### Option 1: Network-Level Throttling via `tc` (Immediate)

Apply a Linux traffic control (`tc`) rate limit on the buildkitd container's network interface:

```bash
CONTAINER=$(docker ps --filter name=buildx_buildkit_multiarch0 --format '{{.ID}}')
PID=$(docker inspect $CONTAINER --format '{{.State.Pid}}')
PEER=$(ip link | grep -A1 "if$(nsenter -t $PID -n cat /sys/class/net/eth0/iflink)" \
  | head -1 | awk '{print $2}' | tr -d ':')

tc qdisc add dev $PEER root tbf rate 10mbit burst 32kbit latency 400ms
```

Remove when done:
```bash
tc qdisc del dev $PEER root
```

**Pros:** Immediate effect, no builder reconfiguration needed.  
**Cons:** Must be reapplied after each builder restart; does not reduce concurrency, only caps throughput.

---

### Option 2: Local Registry Mirror (Recommended Long-Term Fix)

Run a local pull-through registry mirror to cache layers locally, eliminating repeated downloads:

```bash
docker run -d --restart=always -p 5000:5000 \
  -e REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io \
  --name registry-mirror registry:2
```

Update `buildkitd.toml`:

```toml
[worker.oci]
  max-parallelism = 1

[registry."docker.io"]
  mirrors = ["http://localhost:5000"]
```

Recreate the builder:
```bash
docker buildx rm multiarch
docker buildx create --use --name multiarch --config /path/to/buildkitd.toml
```

**Pros:** Eliminates redundant downloads on repeated builds; layers cached locally.  
**Cons:** Requires initial setup and local disk space for the mirror cache.

---

### Option 3: Pre-pull Base Images Before Building

Pull base images using the Docker daemon (which honors `--max-concurrent-downloads`) before invoking `docker buildx build`:

```bash
docker pull <base-image>
docker buildx build .
```

BuildKit will use the already-cached image and skip the parallel pull.

**Pros:** Simple, no infrastructure changes.  
**Cons:** Manual step; must be remembered before every build; not suitable for CI automation.

## Lessons Learned

- `max-parallelism` in `buildkitd.toml` controls **build step concurrency**, not **layer download concurrency**. These are distinct concepts.
- A local registry mirror should be standard practice in bandwidth-constrained environments, especially with multi-platform builders.
- Bandwidth impact should be assessed when setting up new builders, particularly those targeting multiple platforms simultaneously.
